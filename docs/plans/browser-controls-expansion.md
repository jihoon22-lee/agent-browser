# 입력창 실행 선택과 브라우저 제어 확장

상태: **구현 완료, 최종 검증·배포 진행 중** (2026-10-28).

사용자 요청은 모델·에이전트 선택을 입력창으로 옮기는 변경과 브라우저 기능 5개를 함께 검토하고, 안정성을 높일 실행 계획을 먼저 만드는 것이다. 이 문서는 구현 승인을 대신하지 않는다. 계획 수립 때는 정적 검토만 했으며, 2026-10-28부터 사용자의 승인에 따라 구현·검증·배포를 진행한다. 실제 결과는 status.md에 구분한다.

기준: [요구사항](../handoff.md), [상태](../status.md), [현재 지원표](../browser-capabilities.md), [OpenCode v1 계약](../opencode-v1-compatibility.md). 기존 [B10 후속 조사](browser-quality-followup.md)는 별도 미완료 과제로 유지한다.

2026-10-27 후속 합의: **기존 기능은 Chrome 116 이상에서 유지하고, 이번 브라우저 고급 기능 5개는 Chrome 125 이상에서만 활성화할 수 있게 한다.** 입력창 선택 UI는 기존 지원 버전을 유지한다. 사용자는 기능 확장으로 기존 안정성이 떨어지지 않고, 테스트 시나리오 보강으로 더 높아지기를 요구했다. 모델 자동 판정/보조 모델 호출 방식과 수치 기준은 아래 안으로 구현·검증한다.

## 1. 타당성 판단

5개 모두 사용할 수 있는 API와 기존 구조에 연결할 경로가 있다. 다만 API가 있다는 사실과 모든 사이트에서 안정적으로 동작한다는 주장은 구분한다. 아래 범위로 구현 가능하며, 어려운 경계는 P0 실측 후 확정한다.

| 기능 | 판단·예상 난도 | 구현 범위와 전제 |
|---|---|---|
| 입력창 모델·에이전트·추론 옵션 | 가능 / 낮음~중간 | 기존 선택 상태와 v1 요청을 재사용. 좁은 패널, 세션 전환, 응답 중 변경의 적용 시점 검증 |
| ① 텍스트 입력·iframe 강화 | 가능 / 높음 | CDP 텍스트 입력과 프레임별 문서·세션 매핑. 포커스 이동·교차 출처·중첩 프레임·문서 교체가 핵심 |
| ② 화면 기반 좌표 조작 | 가능 / 높음 | 캡처에 결합된 클릭·호버·드래그·휠. 이미지 입력을 지원하는 기존 모델 필요. canvas의 의미 구조를 읽는 기능은 아님 |
| ③ 대화상자 응답 | 가능 / 중간~높음 | 웹페이지의 alert/confirm/prompt 확인·취소·문자 입력. 발생한 원래 동작을 재실행하지 않는 상태 관리 필요 |
| ④ 전체 페이지·영역 캡처 | 가능 / 중간 | CDP 페이지 크기·clip·captureBeyondViewport. 현재 렌더된 문서 크기 기준이며 무한 스크롤 데이터 전체 수집은 아님 |
| ⑤ 다운로드 완료 확인 | 가능 / 중간~높음 | 선택 downloads 권한, 다운로드 ID별 상태 추적. 페이지 클릭과 다운로드의 연결은 별도 검증하며 불명확한 연결은 확정하지 않음 |

기존 Extension + Windows Bridge + OpenCode v1 구조를 유지한다. 별도 브라우저 프로세스, 자체 에이전트 하네스, 범용 CDP/JavaScript 실행 도구, OS 자동화는 추가하지 않는다. DOM 제어를 기본으로 유지하고 시각 제어를 보완 경로로 제공한다.

## 2. 현재 코드에서 확인한 설계 경계

- [Workbench](../../extension/src/sidepanel/Workbench.tsx)의 모델·agent·variant는 이미 다음 메시지의 v1 요청에 들어간다. 선택 UI만 실행 설정 drawer 안에 있다. 검색·즐겨찾기·이전 세션의 선택 복원 기능을 함께 옮겨야 한다.
- [trusted-input](../../extension/src/background/trusted-input.ts)은 최상위 탭 기준 클릭·키·드래그와 화면 캡처만 제공한다. [trusted-message](../../extension/src/background/trusted-message.ts)는 `frameId !== 0`을 거부하며 [handlers](../../extension/src/background/handlers.ts)는 fill에 신뢰 입력을 켜지 않는다.
- 현재 디버거 인터페이스는 tabId만 다룬다. OOPIF(별도 프로세스 iframe)의 sessionId·execution context·문서 수명을 다루는 계층이 필요하다. Chrome frameId/documentId와 CDP FrameId는 같은 식별자가 아니다.
- [manifest](../../extension/public/manifest.json)의 최소 Chrome은 116이다. 공식 확장 디버거의 flat session 지원은 125부터다. 사용자 합의에 따라 기존 기능은 116 이상, 이번 고급 기능 5개는 125 이상으로 구분한다. 기존 신뢰 입력·비활성 viewport 캡처까지 125 전용으로 바꾸지 않는다. 버전은 필요조건이며 디버거 연결·API 가용성·권한도 별도로 확인한다.
- 현재 대화상자 이벤트는 입력 중과 직후에 alert을 확인하고 나머지를 취소한다. 명시 응답을 추가하려면 이 동작과 T02 회귀의 기대값을 변경해야 한다.
- [user-input](../../extension/src/content/user-input.ts)은 `isTrusted` 이벤트를 사용자 개입으로 센다. CDP 입력도 이 경로에 포함될 수 있어 신뢰 입력으로 연 새 탭을 사용자 개입으로 오인할 가능성이 있다. **정적 검토에서 찾은 위험이며 이번에 재현한 결함은 아니다.** 무조건 감시를 끄는 수정 대신 실제 개입과의 경합 검사를 먼저 만든다.
- [Bridge router](../../bridge/src/server/router.rs)는 도구의 읽기/쓰기, operation/generation/currentTab, 재관찰 요구를 관리한다. 새 도구가 이 경계를 우회하면 안 된다. 특히 좌표 조작은 screenshot을 읽기 증거로 인정하는 명시적 계약이 필요하다.
- [MCP 응답](../../bridge/src/mcp/mod.rs)은 browser_screenshot에만 이미지 블록을 붙인다. 이미지는 별도이지만 메타데이터는 텍스트 출력 예산을 지켜야 한다. 큰 이미지의 전송 크기·메모리 제한도 전체 경로에서 점검한다.
- downloads 권한·도구는 없다. 현재 지원표의 “downloads 권한을 추가하지 않음”은 이번 요청에 따른 변경 대상이다. 계획 단계에서는 기존 배포 기능처럼 문구를 바꾸지 않는다.

## 3. 입력창 선택 UI

입력창 하단에 `[현재 모델 ▾] [추론 옵션 ▾] [현재 에이전트 ▾]`를 둔다. 모델이 주 선택이고 에이전트는 작은 보조 선택으로 유지한다.

- 모델 버튼은 별도 실행 설정 화면을 거치지 않고 검색 가능한 선택 목록을 연다. 즐겨찾기 우선, 긴 이름 말줄임·전체 이름 확인, 키보드 이동·Esc·초점 복원을 지원한다.
- 현재 환경에 연결·설정된 모델만 표시한다. 추론 옵션은 선택 모델이 제공할 때만 표시하며 모델 변경 시 호환되지 않는 variant를 초기화한다.
- build/plan 외의 사용자 정의 primary/all 에이전트도 보존한다. 기존 세션과 서버 기본 설정을 존중하고 build를 무조건 강제하지 않는다. plan을 브라우저 도구의 읽기 전용 보장으로 표시하지 않는다.
- 응답 도중 바꿔도 진행 중 호출은 유지하고 “다음 메시지부터 적용”을 표시한다. 새 세션, 기존 세션 복귀, 환경 전환, 이전 모델 사용 불가에서 선택이 섞이지 않아야 한다.
- 실행 환경·디렉터리는 실행 설정에 남긴다. `/models`도 새 모델 선택 목록을 열도록 연결한다. 동일 선택 상태를 drawer와 입력창에 중복 구현하지 않는다.
- 320px 폭·한글·긴 모델명·IME·키보드·확대 배율에서 입력과 전송 공간을 확보한다.
- 빠르게/깊게 프리셋과 모델 자동 전환은 이번 기본 범위에 넣지 않는다. 모델 즐겨찾기로 빠른 전환을 제공하며 특정 모델 ID·성능 등급을 제품에 고정하지 않는다.
- 이미지 지원 여부는 서버 모델 메타데이터로 안내한다. MCP 이미지가 실제 v1 모델 입력까지 전달되는지 별도 계약 검증한다. 이미지 불가/정보 없음은 구분하고 모델을 몰래 교체하지 않는다.

완료 기준: 한 번의 선택 목록 열기로 모델·에이전트를 변경할 수 있고, 다음 요청의 model/agent/variant가 선택값과 일치하며 진행 중 요청·초안·첨부·다른 세션에 영향을 주지 않는다.

### 모델과 실행 환경에 따른 사용 가능 여부 — 권고안

현재 제품에는 이미지 지원에 따른 기능 차단이나 자동 비전 서브에이전트 호출이 없다. v1의 Model에는 `capabilities.input.image`와 `capabilities.toolcall`이 있고 현재 목록 코드가 그 정보를 보존한다. **현재 요청을 실제로 실행하는 모델의 기능을 자동 확인하는 방식부터 구현한다.** 다른 모델이 카탈로그에 있다는 사실만으로 호출 권한이나 그 모델의 현재 가용성을 가정하지 않는다.

| 판단 층 | 규칙 |
|---|---|
| Chrome | 116~124: 기존 기능·입력창 선택 UI 유지, 고급 기능 5개 비활성. 125 이상: 고급 기능 활성화 자격. 버전 미확인은 고급 기능 활성 가능으로 추정하지 않음 |
| 실행 조건 | 디버거가 필요한 기능은 사용자 설정+실제 연결+해당 API 지원 확인. 다운로드 확인은 125 이상+downloads 권한이며 디버거가 필수는 아님 |
| 모델 | `input.image === true`: 이미지 입력 지원으로 표시. false: 미지원. 누락/형식 불명: 지원 정보 없음. 이미지 생성(`output.image`), 음성 지원, 모델 이름만으로 추정하지 않음 |
| 이미지 경로 | 모델의 이미지 입력 표시와 OpenCode/MCP 이미지 전달 경로의 지원을 구분. 이미지+도구 호출이 필요한 자동 시각 작업은 두 조건을 모두 확인 |
| 실제 실패 | 이미지 요청 거부·공급자 오류가 확인되면 해당 환경/모델의 사용 불가 이유를 표시. 결과를 숨기거나 다른 모델로 자동 재실행하지 않음 |

- 모델 선택 시 입력창에 이미지 지원/미지원/정보 없음과 시각 조작 가능 여부를 표시한다. 미지원이면 현재 환경의 이미지 지원 모델만 필터링해 직접 선택할 수 있게 한다. 자동 판정은 메타데이터 조회이며 선택할 때마다 유료 가능성이 있는 시험 추론을 보내지 않는다.
- 이미지 이해가 필요한 것은 **화면을 해석해 좌표를 정하는 자동 시각 작업**이다. 텍스트/iframe 입력·대화상자·다운로드 확인은 이미지 모델을 요구하지 않는다. 캡처 생성·사용자 미리보기/저장은 이미지 이해 없이 가능하지만, 그 이미지를 비전이 없는 모델에게 읽었다고 가정해 넘기지는 않는다. 읽기 캡처와 모델의 이미지 해석 경로를 분리한다.
- 요청 전송 시 실행 모델·에이전트·모델 capability를 요청 ID와 함께 고정한다. 다음 메시지용 모델을 바꾸어도 실행 중인 작업의 권한/기능 판단이 바뀌면 안 된다. UI 표시만 바꾸지 말고 실제 도구 실행 전에도 요청과 실행 조건을 검사한다.
- `/command`가 별도 model/agent를 지정하거나 OpenCode 내부의 다른 실행 주체가 도구를 호출할 수 있으므로, 화면에서 선택한 모델과 실제 호출 모델이 항상 같다고 가정하지 않는다. P0에서 설치본 v1 계약과 호출 전달 정보를 확인한다. 모델을 식별할 수 없는 CLI/외부 MCP 호출은 “정보 없음”으로 취급하며 자동 시각 작업을 지원한다고 주장하지 않는다. 기존 DOM 도구는 계속 제공한다.
- capability는 기능 안내/실행 전제이며 모델의 시각 판단 정확도 인증이 아니다. 실제 이미지 전달 실패는 메타데이터 오류, 서버 경로 문제, 공급자 장애로 분류한다. 선택 설정/환경이 바뀌면 관련 판정을 갱신한다.

### 자동 비전 서브에이전트와의 비교

현재 모델 자동 판정은 비용·지연·컨텍스트·취소 경로가 하나여서 첫 구현과 기존 안정성 유지에 적합하다. 자동 서브에이전트 방식은 텍스트 모델을 주로 쓰면서 이미지 판단만 위임할 수 있지만, 관찰과 조작 사이 지연·이미지 전달·실제 사용 모델/비용 표시·중단 전파·작업 소유·동시 조작을 추가로 관리해야 한다. 현재 구성된 다른 모델 중 하나를 임의 선택하는 방식은 채택하지 않는다.

향후 별도 요구가 있으면 **사용자가 지정한 보조 이미지 모델**에 한해 OpenCode의 기존 위임 기능으로 검토한다. 보조 모델은 이미지 해석/좌표 제안만 하고 브라우저를 동시에 조작하지 않는다. 주 실행자가 captureId의 유효성을 재검사한 뒤 한 번 실행한다. 새 하네스나 Bridge의 직접 LLM 호출은 추가하지 않는다. 이번 기본 구현 범위에는 자동 위임을 넣지 않는다.

## 4. 공통 안정성 설계

### 관찰 → 한 번 실행 → 결과 확인

1. DOM 작업은 기존 ref·문서·대상 동일성 검사를 유지한다. 좌표 작업은 아래 captureId에 결합한다.
2. 입력 직전에 operation·generation·문서·프레임·포커스/좌표를 다시 검사한다. 중단·사용자 넘겨받기·디버거 해제 뒤에는 새 쓰기를 시작하지 않는다.
3. 입력 전 실패, 입력 전송 후 결과 불명확, 입력 후 기대 조건 불충족을 구분한다. `executed`와 `verified`를 혼동하지 않는다.
4. 미전송이 명확한 경우에만 DOM 대체를 허용한다. CDP 응답 유실·부분 전송·timeout 후에는 원래 입력을 반복하지 않고 결과를 관찰한다. 읽기 재시도에도 횟수·전체 deadline을 둔다.
5. 디버거 입력은 탭/입력 경로별로 순서를 보장한다. 다른 명령이 누른 수정키·마우스 버튼을 해제하지 않도록 보유 상태를 추적한다. 부분 실패 뒤 같은 세션이 살아 있으면 해당 명령의 키/버튼 해제만 시도하고, 결과를 원래 동작 성공으로 취급하지 않는다.
6. 클릭·키가 보낸 이벤트와 실제 업무 완료를 분리한다. fill 값 유지, 지정 문구/URL, 대화상자 닫힘, 다운로드 complete 등 기능에 맞는 확인 근거를 반환한다. 입력 이벤트가 성공했다고 서버 저장 성공으로 보고하지 않는다.

### 수명·복구·성능

- 디버거 연결은 탭 단위로 재사용하고 작업 종료·해제·브라우저 넘겨받기 때 정리한다. 하위 세션과 관찰 토큰도 함께 폐기한다.
- 요청 취소·Bridge 재연결·서비스 워커 재시작 뒤 이전 쓰기를 재생하지 않는다. 재생 방지 상태와 결과 조회용 상태를 구분한다. 유지한 다운로드 ID는 현재 Chrome 상태를 다시 조회하되 오래된 operation에 자동 결합하지 않는다.
- 일반 화면 변경을 과도하게 stale로 처리하지 않도록 대상 영역을 중심으로 확인한다. 반대로 canvas 내부 변화는 DOM mutation 감지만으로 확인할 수 없으므로 좌표 실행 직전 영역 재캡처/비교를 설계한다. 화면 확인과 실제 입력 사이의 경합을 완전히 제거한다고 주장하지 않는다.
- `isTrusted` 하나로 사용자/에이전트 입력을 구분하지 않는다. 작업·실행 중 입력·탭 생성 출처 등 근거를 함께 쓰고, 동시에 일어난 물리 입력을 구분할 수 없으면 결과 소유를 불명확으로 남긴다.
- DOM 경로의 도구 비용과 토큰 예산을 유지한다. 그림은 필요할 때만 읽고 전체 페이지 대신 viewport/영역을 우선한다. 고정 sleep 추가나 무조건적인 재시도로 안정성을 대신하지 않는다.

## 5. 기능별 구현안과 완료 기준

### ① 텍스트 입력·iframe 강화

기존 browser_fill/클릭/키 도구를 확장한다. 기존 DOM 경로는 유지하며, 신뢰 입력을 켠 환경에서 대상과 포커스를 검증한 뒤 CDP `Input.insertText` 및 지원되는 편집 명령을 이용한다. insertText는 현재 선택에 삽입하는 API이므로 “전체 값 교체”를 위해 선택 범위 설정과 최종 값 검증이 별도로 필요하다. 빈 문자열 지우기도 따로 검사한다.

- 같은 출처·교차 출처·중첩 iframe을 Chrome 문서 ID와 CDP 실행 문맥/하위 세션에 연결한다. URL이나 프레임 순번만으로 매핑하지 않는다.
- 프레임 이동·삭제·프로세스 변경 시 매핑을 폐기한다. 실행 중 요청은 원래 문서에 묶고 새 문서에 입력을 전달하지 않는다.
- 프레임 좌표는 부모 스크롤·테두리·배율·변환을 포함해 최상위 viewport로 변환한다. 단순 offset 합산에 의존하지 않는다. 변환/가림을 확인할 수 없는 경우 명시적으로 거부한다.
- 입력 직전 activeElement 체인과 원래 대상 동일성을 확인한다. 한글·이모지·여러 줄·선택 교체·빈 문자열·readonly·입력 후 앱이 값을 되돌리는 경우를 검증한다. 실제 OS IME 조합 동작 전체를 제공한다고 표시하지 않는다.
- DOM 경로로 대체했다면 이유를 결과에 표시한다. 입력 후 실패에서 DOM으로 재입력하지 않는다.

완료 기준: 최상위/동일 출처/교차 출처/중첩 프레임의 신뢰 입력 요구 fixture에서 값과 이벤트 횟수가 일치한다. 포커스 탈취·문서 교체·오래된 ref·중단 뒤 다른 입력칸에 쓰는 횟수는 0이다. 프레임 배율/변환 지원 범위를 실측 결과로 문서화한다.

### ④ 전체 페이지·영역 캡처 — 좌표 기능보다 먼저

browser_screenshot에 `scope: viewport | fullPage | region`을 추가하는 안이다. 기본은 기존 viewport이며 영역은 CSS 좌표 사각형 또는 유효한 ref로 지정한다. 두 지정 방식이 동시에 들어오면 거부한다.

- CDP `Page.getLayoutMetrics`의 CSS 지표와 `Page.captureScreenshot`의 clip/captureBeyondViewport를 사용한다. fullPage는 현재 문서의 렌더된 범위이며 가상 목록의 미생성 행까지 채우지 않는다.
- 결과에 captureId, 탭/문서 결합, 이미지 크기, CSS 영역 원점·크기, 배율·스크롤 정보를 붙인다. 모델에는 조작 좌표계를 하나로 명확히 설명한다.
- 실제 PNG 크기와 메타데이터를 검증한다. 전체 픽셀 수·이미지 바이트·처리시간에 상한을 두고, 큰 문서는 영역 분할을 안내한다. 조용히 축소/잘라서 전체라고 반환하지 않는다.
- 캡처 전후 탭·문서·viewport를 비교한다. 다른 활성 탭 이미지를 반환하지 않는다. 사용자 전경 탭과 스크롤 위치를 임의로 바꾸지 않는다.
- 신뢰 입력 꺼짐/디버거 불가에서는 기존 활성 viewport 캡처를 유지하고 고급 범위는 필요한 조건을 설명한다.

완료 기준: 세로로 긴 합성 문서의 위·중간·아래 표식이 fullPage에 있고, region에는 지정 영역만 있다. 다른 탭 활성 상태, 확대, 디스플레이 배율, 이동 중 캡처, 큰 이미지 제한을 검증한다. 고정 헤더·lazy loading·무한 스크롤의 의미와 한계를 안내한다.

### ② 화면 기반 좌표 조작

기존 ref 기반 browser_click은 유지하고 별도 `browser_pointer`를 추가하는 안이다. screenshot에서 받은 captureId와 이미지 픽셀 좌표를 받아 CSS viewport 좌표로 변환한다. 최초 범위는 click/double/right/hover/drag/wheel(수평·수직)이다. 임의 JavaScript나 OS 좌표는 받지 않는다.

- 첫 구현에서 조작 토큰은 현재 viewport와 그 안의 region 캡처에만 발급한다. fullPage는 읽기에 사용하고, 화면 밖 위치는 먼저 스크롤한 뒤 재캡처해 조작한다.
- captureId는 해당 operation/generation/tab/document와 배율·스크롤·화면 상태에 묶는다. 입력 후 또는 이동·resize·zoom·사용자 넘겨받기 뒤에는 재관찰을 요구한다. 새 captureId가 Bridge의 `needs_observation`을 해제하는 조건도 명시한다.
- DOM으로 목표를 찾을 수 있으면 ref 도구를 먼저 쓰도록 안내한다. 화면 기반 제어는 canvas·지도·커스텀 UI 등의 보완 경로다. 이미지 판단은 기존 OpenCode 모델이 수행하고 별도 비전 모델 호출기를 만들지 않는다.
- viewport 범위·가림·대상 영역 변화 확인 후 입력하고 결과를 다시 관찰한다. pointer 결과가 자동으로 캡처를 붙이는지, 별도 screenshot으로 확인하는지는 이미지 예산을 포함해 P0에서 정한다. 이미지 없는 모델에는 화면 판단을 했다고 주장하지 않는다.

완료 기준: canvas 버튼/슬라이더·지도 모형·가로 스크롤 fixture에서 정확한 좌표/최종 상태를 확인한다. 캡처 뒤 스크롤·확대·탭 전환·팝업 겹침·canvas 내용 교체·요청 중단 시 이전 좌표를 재사용하지 않는다. 움직이는 화면과 모델의 오판을 완전히 방지한다는 보장은 제외한다.

### ③ 대화상자 응답

`browser_dialog`의 조회·응답과 패널의 대기 상태를 추가한다. dialogId를 operation·tab·CDP 세션·발생 순서에 결합하고 accept/dismiss/promptText를 명시한다. 사용자 웹페이지의 대화상자와 OpenCode 자체 질문·권한 카드를 구분한다.

- `confirm`·`prompt`를 즉시 취소하는 현재 처리를 대기/명시 응답으로 변경한다. alert은 기본 자동 확인과 결과 알림을 유지하되 명시 처리 경로도 제공한다. beforeunload는 기존 미저장 폼 보호를 유지하고 강제 닫기에 사용하지 않는다.
- 대화상자로 content script 또는 CDP 입력 응답이 막혀도 원래 도구는 `dialogPending`을 반환할 수 있어야 한다. 입력 전송 사실과 완료 조건 미확인을 함께 기록한다. 열린 대화상자 때문에 실패하는 자동 snapshot을 억제하고 후속 응답 도구가 실행될 수 있게 한다.
- 단순 Promise.race 후 기존 입력을 잊지 않는다. 원래 CDP 응답과 실행 결과를 추적하며 대화상자가 닫힌 뒤 재조회로 결과를 확인한다. 명령 순서 보장 장치가 대화상자 응답까지 막는 교착을 만들지 않는다.
- dialogId는 한 번만 응답할 수 있고 연속된 두 대화상자를 혼동하지 않는다. 사용자가 먼저 닫았거나 디버거가 끊기면 오래된 응답을 거부한다. 작업과 연결되지 않은 대화상자는 자동 처리하지 않는다.
- 중단/넘겨받기/해제 시 대기 상태를 알리고 사용자에게 제어를 돌린다. 대기를 끝내려는 목적으로 confirm을 임의 승인하거나 원래 버튼을 다시 누르지 않는다.

완료 기준: 확인·취소·prompt 한글 입력·연속 대화상자·iframe 대화상자·동작 후 지연 발생을 검사한다. alert/confirm 때문에 MCP가 끝없이 기다리지 않으며, 응답 유실·사용자 선응답·중단 후 중복 실행은 0이다. OS 창·Chrome 권한 팝업은 포함하지 않는다.

### ⑤ 다운로드 완료 확인

선택 `downloads` 권한과 `browser_downloads`의 목록/상태/제한시간 대기를 추가하는 안이다. 최초 범위는 현재 작업과 관련된 다운로드 확인이며 파일 내용 읽기·실행·삭제·임의 경로 저장·새 다운로드를 직접 시작하는 범용 도구는 포함하지 않는다.

- 설정의 사용자 클릭에서만 선택 권한을 요청한다. 꺼짐·거부·철회 상태를 표시하고 에이전트 도구가 권한 UI를 대신 승인하지 않는다. 디버거 설정과 별도이며, downloads 권한만으로 조회 가능한 경로를 둔다.
- onCreated/onChanged와 downloadId별 search로 in_progress/complete/interrupted·파일명·크기·오류를 확인한다. bytesReceived는 onChanged 대상이 아니므로 진행량이 필요할 때만 제한된 조회를 한다. totalBytes 미상은 100%로 표시하지 않는다.
- 현재 작업의 클릭 전 관찰을 시작하고, 새 다운로드의 시간·URL/리다이렉트·referrer·이름을 후보 근거로 모은다. DownloadItem에는 원본 tabId가 없으므로 “방금 생김”이나 동일 URL만으로 소유를 확정하지 않는다. 동시 사용자 다운로드와 여러 후보는 `ambiguous`로 남기고 패널에서 해당 항목을 선택해 결합할 수 있게 한다.
- 디버거의 페이지별 다운로드 이벤트는 보조 증거로 검토하되, deprecated인 Page.downloadWillBegin/Progress를 필수 전제로 삼지 않는다. 확장 debugger의 허용 도메인에 없는 Browser 도메인을 사용할 수 있다고 가정하지 않는다.
- 페이지 버튼·POST/리다이렉트·blob 다운로드를 각각 실측한다. 소유 연결이 안 되는 형식도 후보 선택 후 ID별 완료 확인은 가능하게 한다. 디버거 없이도 이 수동 결합 경로가 동작해야 한다.
- 권한이 전체 다운로드 기록을 읽을 수 있어도 기본 도구 결과에는 현재 작업 관찰 창의 후보/결합된 항목만 제공한다. 로컬 절대 경로는 기본 응답 대신 파일명을 쓴다. 일반 다운로드 기록 전체를 LLM에 전달하지 않는다.
- 서비스 워커 재시작 뒤 결합된 ID를 제한적으로 복구하고 조회로 상태를 보정한다. Chrome의 완료는 저장 완료 근거이며 현재 파일 존재·내용 검증과 구분한다. 대기 취소는 다운로드 자체의 취소가 아니다. 기존 다운로드를 재시작하지 않는다.

완료 기준: 빠르게 끝난 다운로드, 지연·중단·동일 이름·동시 사용자 다운로드·리다이렉트·blob·워커 재시작·권한 철회를 검사한다. 잘못된 다운로드를 작업 완료로 보고한 횟수는 0이다. 저장 대화상자나 Chrome 판단 대기 상태를 자동 승인하지 않고 구분한다.

각 단계는 과제 단위 실패 테스트 → 구현 → 직접 영향받는 테스트 → 영어 Conventional Commit 순서로 진행한다. P0에서 특정 API 지원이 없으면 해당 기능의 지원 조건과 대체안을 문서화하고, 임의로 전부 지원으로 표시하지 않는다. 큰 변경을 한 번에 배포하지 않고 단계별로 검토 가능한 결과를 만든다.

## 7. 검증 계획

### 결정적 검사

- Extension 단위: 대상/문서 매핑, 허용된 메시지 발신자, 좌표 변환, 토큰 수명, 이벤트/명령 상태 전이, 실패·취소 경합, optional permission.
- Rust/프로토콜: 새 schema·tools-list fixture·읽기/쓰기 분류·operation 결합·needs_observation·취소/출력 예산. 허용하지 않은 필드나 도구가 경계를 우회하지 않아야 한다.
- 합성 OpenCode v1: 모델/agent/variant·이미지 capability 표시, MCP 이미지 전달, 다음 메시지 적용, 다른 환경/세션의 상태 격리. `/api/*`는 사용하지 않는다.
- Chrome E2E: 위 기능별 완료 기준과 기존 일반 입력·신뢰 입력 on/off를 실제 웹페이지 최종 상태로 검사한다. 단순 도구 ok 응답만으로 통과시키지 않는다.
- Windows: MSVC exe를 WSL에서 cross-build한 뒤 Windows Node·Chrome·실제 exe로 검증한다. 사용자 프로필과 분리된 테스트 프로필을 사용한다. 패널 폭 320/400/600px·한글·100/125/150% 배율의 실제 렌더를 확인하고 Chrome의 권한/디버거 표시줄은 headed 확인 항목으로 둔다. 자동 API 검사를 권한 UI 육안 확인으로 대체하지 않는다.

### 안정성과 비용의 합격 근거

- P0에서 대표 정상/경합 workload의 기준선을 저장한다. 오대상 입력·중복 쓰기·중단 후 새 입력·거짓 업무 완료는 모든 결정적 사례에서 0이어야 한다.
- 최소한 포커스 교체, iframe 교체, 캡처 후 화면 이동, 대화상자 순서 경합, 다운로드 동시 발생을 반복 측정한다. 반복 횟수·조건·최초 실패를 남기며 성공 재실행으로 실패 기록을 덮지 않는다.
- 같은 fixture·환경에서 완료율, 실패 유형, 단계 수, 도구 지연 p50/p95, 전체 작업 시간, 스냅샷 텍스트/이미지 바이트를 전후 비교한다. 고급 기능 때문에 기존 DOM 경로에 불필요한 캡처·대기가 늘지 않아야 한다.
- 실제 LLM 평가는 별도다. 기존 설정을 수정하지 않고 현재 확인되는 Zen 무료 모델만 사용한다. 시각 평가는 이미지 입력+도구 호출을 실제 지원하는 무료 모델이 있을 때만 한다. 공급자 403/이미지 미지원은 도구 실패와 구분하고 유료 모델로 대체하지 않는다.
- 이미지 모델이 없더라도 좌표 도구의 결정적 Chrome 검증은 가능하다. 이 경우 “모델의 화면 판단 검증은 미실행”으로 표시하며 완전한 시각 에이전트 검증 통과로 보고하지 않는다.
- 기존 B10 iframe 표시 대기 문제는 원인 미확인 상태를 유지한다. 재현되면 trace·renderer/프레임 상태·CDP 응답·relay/heartbeat를 함께 수집하고 신규 프레임 기능의 실패인지 구분한다. timeout 확대를 해결로 간주하지 않는다.

### 수치화와 출시 기준 초안

기존 [결정적 측정](../../tests/e2e/browser-metrics.spec.ts)과 [보고서](../../tests/e2e/metrics-report.mjs)는 wrongTarget/falseSuccess/duplicateWrites/postCancelWrites 및 p50/p95를 이미 지원한다. [실제 모델 측정](../../tests/agent/metrics.mjs)은 별도다. 이 체계를 확장하며 아래 수치는 **목표/판정 규칙 제안**이지 이번에 얻은 결과가 아니다.

측정 규칙:

1. **기존 기능 유지**: 같은 합성 fixture/측정 코드로 변경 전과 후를 각각 실행한다. 새 기능 시험은 별도 집계하며 새 테스트를 더해 전체 통과율을 올리는 방식으로 기존 회귀를 가리지 않는다. 테스트/하네스/Chrome/옵션이 달라진 과거 수치를 직접 비교하지 않는다.
2. **안정성 개선**: 새 경합 시나리오를 변경 전에도 가능한 범위에서 실행해 실패를 재현하고 변경 후 해결을 보인다. 양쪽 모두 사고 0이면 “관찰 범위에서 유지, 검증 범위 확대”로 보고하며 숫자만으로 개선됐다고 주장하지 않는다. 정상 완료율·불필요한 거부·복구율의 변화도 같이 본다.
3. **표본**: 개발 중에는 직접 영향받는 테스트만 실행한다. 최종 정상 성능은 시나리오·설정별 워밍업 제외 최소 50개, 가능하면 100개 표본을 전후 같은 수로 수집한다. 중요한 경합 묶음은 준비/입력 직전/전송 직후 등의 결정적 주입 지점과 기록한 seed·지연 조합을 합쳐 각 300회 이상 반복하는 안으로 잡는다. 기존 timing runner의 1~200 표본 제한과 경합 반복 runner는 구분한다.
4. **최초 실패 보존**: 재실행 성공으로 처음 실패를 지우지 않는다. 실패도 지연 통계에 포함하고 timeout/미완료 수를 따로 적는다. 실행하지 않은 지표는 0 대신 미측정으로 남긴다. 한 시나리오가 관찰하지 않은 위험 항목을 임의로 0으로 채우지 않는다.
5. **환경 통제**: 동일 머신/OS/Chrome/headless·배율/입력 모드/워크로드 지문으로 비교하고 실행 순서를 교대한다. 신규 고급 기능 off와 on에서 기존 기능을 모두 비교한다. 서로 다른 브라우저 버전은 각각 자기 기준선과 비교한다. 보고서에는 표본 수·환경·실패 원인·불확실성을 함께 기록한다.
6. **해석 한계**: N회 무사고는 모든 사이트의 무결함 증명이 아니다. 독립·동일 조건의 이항 시행이라는 가정에서 0/N의 실패율 95% 단측 상한은 `1 - 0.05^(1/N)`이다(300회 약 1%, 1,000회 약 0.3%). 경합 fixture 표본은 실사용 분포 전체를 대표하지 않으므로 이 값을 실제 사용자 사고 확률로 옮기지 않는다.
7. **LLM 분리**: 도구 자체의 결정적 신뢰성과 모델 판단의 완료율을 분리한다. 실제 모델은 같은 모델/설정·같은 과제에서 비교하고 공급자 장애를 구분한다. 모델 평가 표본이 적으면 탐색 결과로 적는다. 유료 fallback이나 전역 OpenCode 설정 변경은 하지 않는다.

## 8. 변경 대상과 문서 반영

- UI: Workbench 및 관련 상태/스타일·Options의 디버거 설명/다운로드 권한·브라우저 작업 상태 카드.
- Extension: trusted-input/message, handlers, frames, content actions, dedupe, chrome-api와 새 캡처/대화상자/다운로드 상태 모듈. 테스트 가능하게 책임을 나누되 범용 하네스는 만들지 않는다.
- Bridge/MCP: tools.rs, router.rs, 이미지 응답, 새 fixture와 필요한 프로토콜 타입. 기존 Windows Bridge 역할을 유지한다.
- 문서: 구현된 단계마다 handoff의 추가 합의, browser-capabilities, protocol, user-guide, ui-design, testing, status를 갱신한다. 현재 문서에 남은 구형 “백그라운드 캡처 전부 미지원” 설명도 실제 지원 조건에 맞춘다.
- 설치·업데이트·제거·폴더 ACL 정책에는 기능상 변경이 필요 없다. optional permission/확장 교체·Bridge와의 계약 호환성은 패키징 회귀에서 확인한다.

## 9. 공식 API 근거와 검토 한계

2026-10-27 공식 문서/명세를 확인했다. 최신 API 문서의 존재는 현재 설치 Chrome의 해당 명령 성공을 증명하지 않으므로 P0에서 별도로 실측한다.

- [Chrome debugger: 허용 도메인·프레임·Chrome 125 flat sessions](https://developer.chrome.com/docs/extensions/reference/api/debugger)
- [CDP Input 명세: insertText·dispatchMouseEvent·CSS viewport 좌표](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Input.pdl)
- [CDP Page 명세: getLayoutMetrics·captureScreenshot·JavaScript dialog·deprecated download events](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl)
- [Chrome downloads: 권한·DownloadItem·이벤트·완료 상태](https://developer.chrome.com/docs/extensions/reference/api/downloads)

위 공식 근거는 계획 시점의 조사다. 이후 사용자 승인으로 제품 구현과 단위·Chrome·실제 Windows 검증을 실행했다. 실제 결과·최초 실패·미검증은 [상태 기록](../status.md)에 구분한다.
