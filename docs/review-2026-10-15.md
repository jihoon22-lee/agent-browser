## 0. 사용자 보고와 실사용 기록

## 요약 — 가장 큰 마찰 다섯 가지

1. **모델이 페이지를 제대로 "보지" 못한다.** 스냅샷이 본문 텍스트와 평면 요소 목록으로 분리돼 있다. 그래서 행마다 반복되는 버튼(상세/취소)이 어느 행인지 알 수 없다. 아이콘 버튼·이미지 링크는 이름이 비고, React식 클릭 카드는 목록에서 빠지며, 펼침·선택 같은 상태도 없다. [Chromium]
2. **한 작업에 왕복 호출이 너무 많다.** attach → snapshot → 조작 → (결과는 "바뀌었는지" 여부뿐) → 다시 snapshot을 반복한다. 다른 페이지로 이동할 때도 먼저 snapshot이 필요하다. 여기에 requestId·operationId 절차가 더해져 무료 모델이 쉽게 틀린다. [코드]
3. **입력이 실제 사용자 입력과 다르다.** 클릭·키는 `isTrusted=false`인 합성 이벤트이고, 기본 동작을 JS로 흉내 낸다. 지원 키는 7개뿐이고 조합키·hover·글자 단위 입력·드래그·대화상자 처리가 없다. 리치 에디터는 `textContent` 교체로 사실상 동작하지 않는다. [코드]
4. **설치 마법사가 연결 성공을 확인하지 않는다.** 확장 로드, 64자 토큰 붙여넣기, 프로필 저장, 서버 시작을 사용자가 각기 다른 화면에서 진행한다. 마법사는 어느 단계도 실제로 확인하지 않고 "설정이 끝났습니다"를 띄운다. 업데이트 후 확장 새로고침도 수동이다. [코드]
5. **작업이 보이지 않고 멈춰도 알 수 없다.** 페이지 위 표시, 아이콘 배지, 탭 그룹이 없다. 패널이 닫혀 있으면 권한·질문 요청으로 에이전트가 멈춰도 알림이 없다. 백그라운드 완료 확인이 일시 오류로 진행 중 작업을 끊는 결함도 있다. [코드][재현]

## A. 설치·연결

### A1. 마법사가 연결 성공을 확인하지 않음 (빠른 개선)

- **현재:** "Chrome 확장 추가" 단계는 안내 문구와 경로 복사 버튼뿐이다(`installer/SetupForm.cs:67-73`). [다음]은 확장 로드 여부와 무관하게 페어링 단계로 넘어간다(`SetupForm.cs:90`). 페어링 단계도 토큰을 보여 주고 "연결되었다는 표시가 보이면 [다음]"이라고 안내할 뿐이다(`:74-78`). OpenCode 단계는 "설정을 마쳤으면 [다음]"(`:79-82`)이고, 마지막 화면은 무조건 "설정이 끝났습니다"다(`:83-85`).
- **증상:** 확장 경로를 잘못 골랐거나, 토큰 붙여넣기에 실패했거나, 프로필 서버가 시작되지 않아도 마법사는 성공처럼 끝난다. 사용자는 패널을 열고 나서야 실패를 알게 된다.
- **제안:**
  - 페어링 단계에서 Bridge 상태를 폴링해 "확장 연결됨 ✓ / 대기 중"을 실시간으로 보여 준다(Bridge `doctor --json`의 extension 검사나 새 `status` 명령).
  - 연결되면 자동으로 다음 단계로 넘어간다.
  - 마지막 단계를 "연결 점검"으로 바꿔 `doctor`를 실행한다. Bridge·확장·프로필 준비·browser MCP 연결을 목록으로 보여 주고, 실패 항목에는 바로가기 버튼을 둔다.
- **비용·위험:** 낮다. doctor 경로가 이미 있다(`bridge/src/runtime/mod.rs:363-397`, `conn.rs:556-563`).

### A2. 토큰 수동 복사를 없애는 자동 페어링 (구조 개선)

- **현재:** 마법사가 64자 토큰을 보여 주면, 사용자가 확장 옵션을 직접 찾아 열고 붙여 넣은 뒤 저장한다(`SetupForm.cs:155-158`, 확장 `options/App.tsx`). Bridge는 hello에 토큰이 실리면 거부한다(`conn.rs:233`).
- **제안:** 마법사가 짧은 **페어링 창**(예: 120초)을 연다. 그 동안 Bridge는 manifest `key`로 고정된 확장 ID의 origin에서 온 `pair.request`에만 토큰을 넘긴다. 미페어링 확장은 해당 포트로 `pair.request`를 주기적으로 보낸다. 사용자는 마법사의 "Chrome 연결" 버튼을 누르고 확장 쪽 승인만 하면 된다.
- **위협 모델:** 같은 사용자 권한의 로컬 프로세스는 이미 `data\config.json`을 읽을 수 있다. 그래서 짧은 창 + 고정 origin은 기존에 받아들인 위험을 넓히지 않는다. 토큰을 `chrome-extension://…#token=` URL로 넘기는 방식은 Chrome 방문 기록(동기화 가능)에 비밀이 남으므로 쓰지 않는다.
- **확인 필요:** Chrome을 명령줄로 띄워 확장 페이지를 여는 동작은 확인하지 않았다. [추정]

### A3. 업데이트 후 확장 자동 새로고침 (빠른 개선)

- **현재:** Bridge는 hello 응답에 `serverVersion`을 담지만(`conn.rs:324`) 확장은 이 값을 쓰지 않는다(`extension/src`에 `serverVersion`·`runtime.reload`가 없음). 업데이트 안내 5단계가 "chrome://extensions에서 새로고침"이다(`README-install.md` §4).
- **제안:** 압축해제 확장은 설치 폴더를 직접 로드하므로 `chrome.runtime.reload()`로 새 파일을 읽어 온다. 연결 시 `serverVersion > manifest.version`이면 한 번 reload한다. 루프를 막기 위해 "이 Bridge 버전으로 reload했음"을 `storage.local`에 기록하고, 같은 버전으로는 다시 reload하지 않는다. 진행 중 요청이 있으면 끝난 뒤에 한다.
- **비용:** 낮다. 수동 단계 하나와 "확장·Bridge 버전 불일치" 문제 유형 전체가 사라진다.

### A4. 설치기 오류 메시지가 영어로 섞여 나옴 (빠른 개선)

- **현재:** 마법사 UI는 한국어인데, 엔진 예외 상당수가 영어 그대로 상태 영역에 표시된다. 예:
  - "Choose an absolute dedicated installation folder."(`InstallerEngine.cs:72`)
  - "Installation ownership marker is invalid."(`:82`)
  - "An unowned file blocks installation"(`:181`)
  - "No owned installation was found…"(`:149`)
  - `ProfileForm.cs:65`
- **제안:** 사용자에게 보이는 예외를 한국어 문구와 **다음 행동**(무엇을 하면 되는지)으로 바꾼다. 진단용 원문은 상세 보기로 남긴다.

### A5. 프로필 등록 3단계와 "Options에서 시작하세요" (빠른 개선)

- **현재:** 프로필 창에서 [후보 찾기]를 직접 눌러야 하고, [확인] → [프로필 저장]을 거친다. 저장 뒤에는 "Chrome Options에서 선택하고 시작하세요"라고 안내한다(`ProfileForm.cs:18,25,34,40-42`). 작업 폴더 기본값은 홈 폴더다(`:24`).
- **제안:**
  - 창을 열 때 자동으로 탐색하고, 후보가 하나면 미리 채운다.
  - [저장하고 시작]을 한 번 누르면 `runtime start`까지 실행하고 MCP 연결을 확인한 결과를 같은 창에 보여 준다.
  - 작업 폴더는 폴더 선택 대화상자로 고르게 한다.

### A6. 개발자 모드·압축해제 로드 안내 보강 (빠른 개선, 근본 해결 불가)

- **현재:** 경로 복사 버튼만 있다. Web Store나 엔터프라이즈 정책 없이 이 단계를 없앨 방법은 없다.
- **제안:**
  - 단계별 스크린샷이나 짧은 그림 안내를 넣는다.
  - [Chrome 확장 페이지 열기] 버튼을 둔다(명령줄 동작은 확인 필요 [추정]).
  - 확장이 처음 Bridge에 접속을 시도하면(origin이 고정 ID이므로 핸드셰이크 거부 전에도 식별 가능) 마법사에 "확장 감지됨"을 표시한다. A1과 결합한다.

## B. 실제 브라우저 작업

### B1. 스냅샷 품질 — 모델이 대상을 식별할 수 없음

로컬 Chromium에서 주문 목록·카드·탭·슬라이더가 있는 합성 페이지의 실제 출력은 아래와 같다. [Chromium]

```text
s1760500000000001f0e1    button    "메뉴"
s1760500000000001f0e2    link      ""          ← <a><img alt="쇼핑몰 홈"></a>
s1760500000000001f0e3    button    ""          ← <svg><title>장바구니</title></svg> 아이콘 버튼
s1760500000000001f0e6    button    "상세"      ← A-1001 행? (맥락 없음)
s1760500000000001f0e7    button    "취소"
s1760500000000001f0e8    button    "상세"      ← A-1002 행?
...
s1760500000000001f0e12   tab       "전체"      ← aria-selected 상태 없음
s1760500000000001f0e14   slider    "평점"      ← aria-valuenow 없음
s1760500000000001f0e15   button    "필터 열기" ← aria-expanded 없음
(누락) cursor:pointer 카드 2개, contenteditable="plaintext-only" 입력란
```

| 항목 | 현재 | 제안 | 구분 |
|---|---|---|---|
| 이름 계산 | aria-label → labelledby → label → placeholder → innerText → title(`dom.ts:33-59`). `img alt`, SVG `title`, `aria-describedby`, `value`(버튼 외) 미사용 | 자식 `img[alt]`, `svg title`, `aria-describedby`를 추가하고, 이름이 비면 가까운 레이블·제목을 보조로 붙인다 | 빠른 개선 |
| 클릭 후보 | 고정 selector + `onclick` 속성 + tabindex(`dom.ts:1-3`). React는 핸들러를 루트에 달아 속성이 없다 | `cursor:pointer`이면서 조상이 이미 후보가 아닌 요소를 넣는다. `role=combobox/textbox/searchbox/menuitemcheckbox/menuitemradio/treeitem/gridcell/spinbutton/listbox`, `contenteditable=plaintext-only`, `label`, `details`도 넣는다 | 빠른 개선 |
| 상태 | value/checked/disabled만(`snapshot.ts:4,70-81`) | `expanded`·`selected`·`pressed`·`current`·`valuenow`·`required`·`invalid`·`focused`를 넣는다(짧은 키로) | 빠른 개선 |
| 행 맥락 | 본문 텍스트와 요소 목록이 분리돼 있다. 표는 `extract`도 셀 텍스트만 돌려주고 ref가 없다(`extract.ts:7-42`) | 요소마다 `context`(가장 가까운 행·카드·제목의 짧은 텍스트, 예: `"A-1002 · 키보드"`)를 붙인다. 장기적으로는 B1-구조처럼 본문 안에 ref를 넣는다 | 빠른~구조 |
| 참조 길이 | `snapshotId = Date.now()*1000`(`background/dedupe.ts:105`)이라 ref가 22자다. 이 예에서는 JSON의 약 28% | snapshot 안에서만 짧은 번호(`e12`)를 쓰고, 스냅샷 ID는 응답 머리에 한 번만 둔다. Bridge·확장이 "가장 최근 스냅샷"으로 해석한다(옛 ref 거부 규칙은 유지) | 빠른 개선 |

**B1-구조 (계층형 인라인 스냅샷):** 평면 목록 대신 랜드마크·제목·목록·행 단위로 들여 쓴 텍스트 안에 ref를 넣는다.

```text
- 표 "주문 목록"
  - 행: A-1001 | 무선 마우스 | 배송중 | [button 상세 e6] [button 취소 e7]
```

Playwright MCP의 aria snapshot과 같은 방식이다. 모델이 "A-1002의 취소"를 정확히 고를 수 있고, 같은 정보량이면 토큰도 줄어든다. 요구사항 §10("DOM 표현을 Accessibility Tree와 동일하다고 표시하지 않는다")은 지키고, `note`에 DOM 기반임을 계속 밝힌다. 기존 페이지 단위 커서(offset/elementOffset/frameOffset)는 하나의 커서로 통합할 수 있다.

**B1-검색:** 요소가 150개를 넘으면 모델이 elementOffset으로 넘겨 가며 찾아야 한다. `browser_snapshot`에 `query`(텍스트·역할 필터)를 추가하면 원하는 영역만 받을 수 있다. 새 도구를 만들지 않고 기존 도구의 매개변수로 넣는다(스키마 예산은 C절).

### B2. 왕복 호출과 의례 절차 줄이기

| 항목 | 현재 | 제안 | 구분 |
|---|---|---|---|
| 조작 결과 | click은 `{urlChanged, domChanged}`만 반환(`content/actions.ts:48-58,137`). 다음 단계를 위해 반드시 snapshot을 다시 호출한다 | 조작 후 변화가 있으면 **새 스냅샷(또는 바뀐 부분 요약)**을 결과에 붙인다. 결과에 받은 ref는 바로 다음 쓰기에 쓸 수 있게 바인딩한다 | 구조 |
| attach | 탭 정보만 반환(`router.rs:337-344`). 항상 이어서 snapshot이 필요하다 | attach 결과에 첫 스냅샷을 포함한다(선택 매개변수 또는 기본값) | 빠른 개선 |
| 이동 전 snapshot | 일반 웹 탭에서 goto도 `requireSnapshot`(`background/handlers.ts:221`). 문서화된 이유는 없다(`protocol.md:185`는 제한 페이지 예외만 다룬다) | 이 검사가 "보지 않은 편집 내용을 버리지 않기" 위한 것이라면, 닫기에서 쓰는 편집 상태 검사(`close-check`)로 바꾼다. 편집이 없으면 바로 이동한다 | 빠른 개선 |
| requestId/operationId | 모델이 패널 지시문의 requestId를 복사해 attach/new에 넣고, 이후 operationId를 계속 전달해야 한다(`mcp/tools.rs:12,16`, `sidepanel/request-target.ts:17`의 긴 지시문). 누락·오용 복구 사례가 별도 회귀(J12)로 있을 만큼 자주 틀린다 | **가드를 둔 자동 결합**. 관리 런타임 실행 시 overlay의 MCP 환경에 런타임 인스턴스 ID를 넣는다(`runtime/mod.rs:195`). MCP 프록시가 hello에서 이를 밝히면 serve가 런타임을 식별한다. 그 런타임에 활성 패널 요청이 정확히 하나이고 **같은 런타임의 다른 세션이 busy가 아닐 때만** requestId 생략을 그 요청으로 해석한다. 아니면 지금처럼 명시 requestId를 요구한다. 그 요청의 첫 페이지 도구 호출에 operationId가 없으면 캡처된 탭으로 암묵 attach한다 | 구조 |

자동 결합의 전제(요구사항 §11): MCP 연결만으로 OpenCode 세션을 식별할 수 없다. `browser-bridge attach --profile`로 같은 관리 서버에 CLI가 붙을 수 있고, 한 런타임의 세션들이 MCP 프로세스를 공유한다. 그래서 위 가드 없이 자동 결합하면 §11이 금지하는 "다른 세션의 작업을 가로채는" 설계가 된다. 가드가 성립하지 않으면 지금의 명시 절차로 돌아간다.

### B3. 입력 충실도 — 선택형 CDP 입력 계층 (구조 개선)

- **현재:**
  - 클릭은 pointer·mouse 합성 이벤트다(`actions.ts:112-138`).
  - 키는 7개만 지원하고 Enter 제출·Tab 이동·Space 클릭 같은 기본 동작을 JS로 다시 구현한다(`keyboard.ts:74-181`).
  - contenteditable 입력은 `textContent` 교체다(`actions.ts:154-160`). ProseMirror·Draft·Slate·Quill 같은 에디터는 내부 상태가 바뀌지 않는다.
  - hover(호버 메뉴), 조합키(Ctrl+A, Ctrl+Enter), Delete·Home·End·PageDown·좌우 화살표, 글자 단위 입력(자동완성), 더블·우클릭, 드래그, 파일 업로드가 없다.
  - JS `alert/confirm/prompt`는 처리 경로가 없다. 대화상자가 페이지 스레드를 막으면 content 응답이 15초 timeout → `EXECUTION_UNKNOWN`이 되고 사용자가 직접 닫아야 할 것으로 보인다. [추정]
- **근거 조항:** 요구사항 §10 [R10]은 "DOM 방식으로 시작하고, 실제 대상 페이지에서 막히는 사례가 확인되면 Extension 내부의 선택적 chrome.debugger/CDP 제어를 검토한다"고 했다. 지금의 사용자 불만이 그 조건이다. 사용 안내·`status.md:412`의 "debugger 권한을 추가하지 않는다"는 현재 구현의 제한을 적은 문장이고, 사용자 결정 기록은 아니다.
- **제안:** `optional_permissions`에 `debugger`를 넣고, 설정에서 사용자가 켜면 작업 탭에 한해 attach한다. 꺼져 있으면 지금의 DOM 방식으로 동작한다.
  - `Input.dispatchMouseEvent`/`dispatchKeyEvent`/`insertText`: 신뢰 입력과 브라우저 기본 동작. 조합키·hover·드래그·글자 단위 입력이 자연스럽게 해결되고, `keyboard.ts`의 기본 동작 재구현 대부분을 걷어낼 수 있다.
  - `Page.handleJavaScriptDialog`: alert/confirm 처리를 결과로 보고.
  - `Page.captureScreenshot`: 비활성 탭·전체 페이지 캡처. `NEEDS_TAB_ACTIVATION`(`handlers.ts:226`)이 사라진다.
  - `DOM.setFileInputFiles`: 사용자가 패널에서 고른 파일만 업로드. 경로를 모델이 정하지 않는다.
- **비용·위험:**
  - attach한 탭마다 "AgentBrowser가 이 브라우저를 디버깅하는 중" 정보 표시줄이 뜬다.
  - DevTools가 열린 탭과 충돌한다.
  - 권한 경고 문구가 강하다.
  - 작업이 끝나면 즉시 detach해야 한다.
  - 기존 ref·편집 보호 규칙(snapshot 바인딩, 쓰기 불확실성)은 그대로 둔다. 좌표는 ref 기준으로 계산한다.

**CDP 없이 바로 할 수 있는 보강:**
- 리치 에디터 입력을 `textContent` 대신 "포커스 → 전체 선택 → `document.execCommand('insertText')`"로 바꾼다. 대부분의 에디터가 beforeinput/input 경로로 받아들인다. [추정, 사이트별 확인 필요]
- `browser_press`에 `modifiers`와 키 몇 개(Delete·Home·End·PageUp·PageDown·ArrowLeft/Right)를 추가한다.
- `browser_fill`을 텍스트 계열 input으로 제한한다(현재는 submit/checkbox 값도 바꿈, `actions.ts:143-152`).

### B4. 작업 가시성과 사람 개입

| 항목 | 현재 | 제안 |
|---|---|---|
| 페이지 위 표시 | 없음(content·background에 overlay·badge·tab group 없음) | 작업 탭에 얇은 테두리·"에이전트 작업 중" 배지를 띄운다(content script, 페이지 이벤트에 영향 없는 pointer-events:none). 클릭·입력 직전 대상 요소를 짧게 강조한다 |
| 확장 아이콘 | 상태 표시 없음 | `chrome.action.setBadgeText`로 실행 중 ●, 응답 필요 ! 표시. 새 권한이 필요 없다 |
| 작업 탭 묶음 | 없음 | 선택: operation 탭을 "AgentBrowser" 탭 그룹으로 묶는다(`tabGroups` 권한 추가 필요) |
| 패널 닫힘 중 권한·질문 | background에 OpenCode permission/question 처리가 없다(`background/index.ts`, `panel-requests.ts`). 에이전트가 응답을 기다리며 조용히 멈춘다 | 활성 요청이 있을 때 background가 그 세션의 `/permission`·질문 목록을 주기적으로 확인한다(이미 15초 reconcile이 있음). 있으면 배지·알림을 띄우고, 클릭하면 패널을 연다 |
| 수동 인계·재개 | 맨 위 [중단]만 있다. 로그인·캡차 같은 사람이 할 단계 뒤에 이어 갈 방법이 없다(요구사항 §16 "전체 중단과 수동 인계"는 초기 필수) | [잠시 넘겨받기]: 게이트를 일시 정지하고 사용자가 조작하게 한 뒤 [이어서 진행]으로 최신 snapshot부터 재개한다. 모델이 "사용자 개입 필요"를 요청할 수 있는 결과 코드도 둔다 |

### B5. 결함 — 실제 작업을 끊는 문제 (앞선 리뷰에서 재현)

- **(중간) [재현] 일시적 `error` 상태로 진행 중 요청이 끊김.** 백그라운드 reconcile이 15초 timer와 1분 alarm으로 돈다. 이때 `runtime.status`가 `state:'error'`를 한 번 돌려주면 세션이 busy여도 `request.end(abort:true)`를 보낸다(`panel-requests.ts:180,193`). error 분기는 모두 살아 있는 프로세스다(`runtime/mod.rs:323-338`). 원인 후보는 health의 3초 제한(`:681`)과 매번 받는 `/doc` 약 825KB, MCP 미연결, WSL 확인 5초 제한(`:647`)이다. F1 규칙(`status.md:339`)의 의도는 사라진 런타임 정리이므로, 자동 확인 경로는 `error`를 "유지"로 다뤄야 한다. 상태 확인 비용도 `/doc` 결과를 런타임 인스턴스별로 캐시해 줄인다.
- **(낮음) `browser_fill`이 텍스트가 아닌 input도 바꿈** — B3에 포함했다.
- **(낮음) 요청이 없는데 옛 requestId를 쓰면** "패널 요청이 브라우저를 사용 중이니 기다리라"는 안내가 나간다(`server/operation.rs:73-78`). 모델이 없는 요청을 기다릴 수 있다.
- **(낮음~중간) [재현] 외부 서버 주소를 바꿔도 이전 비밀번호가 유지됨**(`runtime/profile.rs:182-185`). 브라우저 작업과는 별개다.

## C. 패널 첫 사용

- **[코드] 세션 없이 보내면 실패한다.** 전송 시 "새 세션을 만들거나 기존 세션을 선택하세요" 오류가 난다(`sidepanel/Workbench.tsx:169`). 첫 전송이면 자동으로 세션을 만든다(`createSession`이 이미 있음, `:108`).
- **[문서] 예시 프롬프트가 지나치게 절차적이다.** 사용 안내의 첫 작업 예시(`docs/user-guide.md` §3)는 탭 확인·연결·금지 동작·중복 처리까지 사용자가 지시한다. 이는 B1·B2 문제를 사용자 지시로 보완하는 증상이다. B1·B2 개선 뒤에는 "현재 페이지 요약해줘" 수준이 동작해야 한다.
- 모델·에이전트 기본값 선택 경로(`Workbench.tsx:88`)는 있으나, 첫 실행 전체 흐름은 자세히 보지 않았다.

## D. 제약 — 제안을 실행할 때 반드시 같이 다룰 것

- **도구 스키마 예산:**
  - 현재 도구 설명+스키마가 **5,987자**다. `tools.rs:92-95`가 6,000자를 넘으면 실패하도록 고정돼 있다(무료 모델 고려).
  - 위 제안의 매개변수 추가(`query`, `modifiers`, hover 등)는 먼저 설명문을 줄이거나 예산을 의식적으로 조정해야 한다.
  - B2의 자동 결합이 성공하면 requestId 관련 설명(현재 가장 긴 문장들)을 크게 줄일 수 있어 예산이 생긴다.
- **요구사항 §11:** 세션을 추측해 결합하지 않는다(B2 가드).
- **요구사항 §10:** DOM 표현을 Accessibility Tree라고 부르지 않는다. 고정 sleep 대신 관찰 가능한 조건으로 기다린다.
- **ref 안전 규칙 유지:**
  - 새 snapshot 전 쓰기 거부, 문서·작업 경계, 쓰기 불확실성(`EXECUTION_UNKNOWN`)은 사용성 개선 중에도 약화하지 않는다.
  - 결과에 스냅샷을 붙이는 방식(B2)은 그 결과를 정식 snapshot 바인딩으로 등록해야 한다.
- **설치 호환성(AGENTS.md):** 자동 페어링·연결 점검에 경로 소유자·ACL 검사를 덧붙이지 않는다.

## E. 통합 로드맵 — 모든 항목의 배치

결함 리뷰(오전)와 이 사용성 리뷰, 사용자 보고를 합쳤다. 네 개의 독립 계획으로 나누고, 각 계획은 그 자체로 테스트·배포 가능한 단위다. 계획 1(브라우저 신뢰성)과 계획 2(설치·첫 사용)는 단계별 계획으로 작성해 완료했다(계획 문서는 Git 이력에 있다). 계획 1과 독립적이다. 계획 3·4는 계획 1의 결과(스냅샷 형식, 결과에 붙는 스냅샷)에 의존하므로 계획 1 뒤에 같은 형식으로 작성한다. 릴리스 시점은 사용자가 정한다. 계획 문서에는 버전 변경 단계를 넣지 않는다.

### 계획 2 — 설치·첫 사용 경험

- **프로필 단계 재설계(A5, §0):** 마법사 페이지 안에 직접 넣는다. 자동 탐색, 로그인 셸 탐색(`bash -lc`), 꺼진 배포판을 켜는 명시 버튼, 폴더 선택 상자, [저장하고 연결 확인] 한 번으로 저장·기본 지정·시작·MCP 확인까지 한다. 배율 대응 배치도 넣는다.
- **연결 실시간 확인과 마지막 연결 점검(A1).**
- **자동 페어링 창(A2).**
- **업데이트 후 확장 자동 새로고침(A3).**
- **한국어 오류와 다음 행동 안내(A4).**
- **확장 로드 안내 보강(A6).**

### 계획 3 — 구조 개선

- **가드 있는 requestId 자동 결합과 암묵 attach(B2, §11 조건).**
- **계층형 인라인 스냅샷과 `query`(B1).** 2026-10-16 측정(fixture 8개 페이지, 최종 텍스트 기준 인라인 outline 19% 절감, 문장이 많은 페이지 6%)에 따라 형식 변경은 보류하고 `query`·후속 스냅샷 상한으로 대체했다. 근거는 계획 3B.
- **작업 가시성:** 아이콘 배지, 작업 탭 테두리, 조작 대상 강조(B4). 계획 3C로 반영.
- **패널이 닫혀 있을 때 권한·질문 알림(B4).** 계획 3C로 반영.
- **수동 인계·재개(B4, 요구사항 §16).** 계획 3C로 반영.

### 계획 4 — 선택 권한(설정에서 켬)

- **`debugger`(CDP) 입력 계층(B3, 요구사항 §10 R10):** 신뢰 클릭·hover·드래그·글자 단위 입력·조합키, alert/confirm 처리, 비활성 탭·전체 페이지 캡처, 사용자가 고른 파일 업로드. 계획 4로 신뢰 클릭·키, 대화상자 처리, 비활성 탭 캡처를 반영했다(Chrome은 debugger를 선택 권한으로 허용하지 않아, 기본 권한에 두고 설정으로 켠다). hover·드래그·조합키·파일 업로드는 계획 5로 반영했다. 파일 업로드는 OS 파일 선택 대신 사용자가 그 요청에 첨부한 파일만 쓴다. 글자 단위 입력·전체 페이지 캡처는 남았다.
- **`tabGroups`:** 작업 탭 묶음(B4). 계획 4로 반영.

각 계획은 AGENTS.md대로 실패하는 테스트를 먼저 쓴다. 브라우저 동작 변경은 합성 fixture와 실제 Windows Chrome E2E로 검증한다. 계획 1의 결과는 사용자가 다시 써 보고 계획 2 착수 전에 우선순위를 조정한다.
